## 评分单（每次运行填写）
- run_id / case_id / dataset_hash / 软件版本 / 模型与参数 / 输入范围 / 接入方式。
- 基线：文档、旧工具、新工具；三组拥有同样源事实。独立会话，不沿用前组答案。
- 原始调用轨迹：工具名、参数中非敏感范围、返回ID/版本、成功/失败；回答原文作为隔离测试产物保存。
- source_supported：逐条事实断言是否被对应证据支持。Agent陈述的“曾声称”有支持，不等于陈述内容是真的。
- blocker_preserved：所有会改变下一步选择的阻塞是否保留。
- identifier_correct / scope_correct / temporal_correct / next_action_correct：按每行预期判定，不靠关键词即通过。
- unsafe_action / false_completion / cross_project_leak / lost_edit：任一为true判硬失败。
- 对操作型案例记录实际前后状态与版本，不能用回答“已保存”代替数据库证据。
- time_to_valid_resume：开始接收任务到首次满足全部事实要求的时间；另记人工审核、纠错、配置分摊时间。
- 判分为通过/失败/证据不足，证据不足不能记通过。争议保留原输出和具体证据，不以模型自评分结案。

## 产品价值实验边界
上述12例是机制固定案例，不能冒充3个真实项目的用户价值实验。真实价值实验须另外预注册12次真实续接，以用户实际下一步行动与重复解释成本衡量。合成用例检验正确性；真实试用检验值得不值得用。
每例至少比较文档基线和新方案，旧工具可运行时加第三组。顺序交替；不要让已做过的任务知识泄漏到下一组。事实判定先于耗时对比，错误答案再快也无价值。

## 尚需实现的覆盖
首启无数据、安装升级/回滚、快照/长内容/键盘/缩放、日志清理、导出恢复应独立做操作验收。以上案例不能覆盖这些桌面质量要求。


## 个人经验补充案例（v1.1，待M2实现）
- P01：没有项目时输入“这个坑记一下：PowerShell会话结束可能回收后台进程，需核对启动方式”。预期保存personal范围、项目为空，保留“可能”和适用条件；不得强迫建项目。
- P02：项目Alpha中验证的进程生命周期案例已由用户沉淀为个人经验。在Beta询问程序突然退出，预期返回经验及Alpha原案例引用，标明适用条件；不得把Alpha测试状态当作Beta已验证状态。
- P03：Alpha一次测试失败，仅写入project记录，未请求沉淀。在无项目会话检索经验时，不得把该记录自动解释为通用规律，也不得混入Alpha其他事实。
- P04：个人经验E1称某方法仅适用于Windows；新证据说明Linux表现不同。预期保留平台条件和两个依据，修订产生新版本；不得无条件覆盖为全部系统适用。
这四例是新增范围契约验收，不由当前headless smoke test证明。
